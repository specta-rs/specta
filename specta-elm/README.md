# Specta Elm

![Crates.io](https://img.shields.io/crates/v/specta-elm?style=for-the-badge)
[![Documentation](https://img.shields.io/docsrs/specta-elm/latest?style=for-the-badge)](https://docs.rs/specta-elm)
![License](https://img.shields.io/crates/l/specta-elm?style=for-the-badge&color=yellow)

Export your Rust types to [Elm](https://elm-lang.org), built on top of
[Specta](https://github.com/specta-rs/specta).

> `specta-elm` is an early release. It is maintained in the official Specta
> repository, but has had far less real-world use than the TypeScript exporter.
> Bug reports and test cases from Elm users are very welcome.

`specta-elm` was created by [vivi](https://codeberg.org/itsvivi),
who designed and published it as a standalone crate before it moved into the
Specta repository.

## Exporters

- **Single File** — every type is written into one module, such as `Types.elm`.
- **Msg File** — shorthand for `SingleFile("Msg")`, for projects following the
  [Elm architecture](#the-elm-architecture).

A multi-file exporter is planned but not implemented yet.

## Unsupported types

Elm has no representation for these, so exporting one returns an error instead of
writing code which won't compile:

- generics
- recursive types
- opaque references
- intersection types, such as Serde's `flatten`
- tuples with more than three elements
- `usize`, `isize`, `i64`, `u64`, `i128`, `u128` and `f128`, which don't fit in
  Elm's `Int`

Elm also shares one namespace between types and constructors, so a type named
`User` and an enum variant named `User` cannot coexist in the same generated
module. Rename one of them with `#[specta(rename = "...")]`.

## Quick Start

```toml
[dependencies]
specta = { version = "2.0.0-rc.28", features = ["derive"] }
specta-elm = "0.1"
```

Define your Rust types:

```rust
use specta::Type;

#[derive(Type)]
struct User {
    id: u32,
    name: String,
    surname: Option<Surname>,
    email: Option<String>,
    role: UserRole,
}

#[derive(Type)]
enum Surname {
    Spanish(String, String),
    Other(String),
}

#[derive(Type)]
enum UserRole {
    Guest,
    Member { permissions: Vec<String> },
    Admin { level: u8, department: String },
}

#[derive(Type)]
enum ApiResult {
    Success { data: String, status: u16 },
    Error { message: String, code: u32 },
    Loading { progress: f32 },
}
```

Then export them into an existing Elm project:

```rust
fn main() {
    let types = specta::Types::default()
        .register::<User>() // also registers `Surname` and `UserRole`
        .register::<ApiResult>();

    specta_elm::Elm::init(types, "./frontend")
        .unwrap()
        .export(specta_elm::exporter::MsgFile)
        // .export(specta_elm::exporter::SingleFile("Msg")) <--- equivalent
        .unwrap();
}
```

`Elm::init` reads the project's `elm.json`, and the exporter writes into its
first source directory. This generates `frontend/src/Msg.elm`:

```elm
module Msg exposing (..)
-- generated by specta-elm

type ApiResult
    = Success { data: String, status: Int }
    | Error { message: String, code: Int }
    | Loading { progress: Float }

type Surname
    = Spanish ( String, String )
    | Other String

type UserRole
    = Guest
    | Member { permissions: List String }
    | Admin { level: Int, department: String }

type alias User =
    { id: Int
    , name: String
    , surname: Maybe Surname
    , email: Maybe String
    , role: UserRole }
```

## Type Mapping

| Elm           | Rust                                                |
| ------------- | --------------------------------------------------- |
| `Int`         | `i8`, `u8`, `i16`, `u16`, `i32`, `u32`              |
| `Float`       | `f16`, `f32`, `f64`                                 |
| `Bool`        | `bool`                                              |
| `String`      | `String`, `&str`, `char`                            |
| `Maybe`       | `Option<T>` and `#[specta(optional)]` fields        |
| `( A, B )`    | `(T, U)` and `(T, U, V)`                            |
| `List`        | `Vec<T>`, slices                                     |
| `Set`         | `HashSet<T>`, `BTreeSet<T>`                         |
| `Dict`        | `HashMap<K, V>`, `BTreeMap<K, V>`                   |
| `()`          | unit structs and empty tuples                       |

## The Elm architecture

In the Elm architecture an application has three main pieces: model, view and
update. The model is the application state, the view renders it as HTML, and the
update function produces a new model from a `Msg`.

Because `Msg` is the type which carries data between those pieces, exporting
everything into a single `Msg.elm` module lets an application import every
generated type at once:

```elm
import Msg exposing (..)

type alias Alias = Msg.SomeType

type alias RedundantAlias = SomeType
```

A multi-file exporter would match Elm's naming conventions more closely, with
one module per generated type:

```elm
import SomeType exposing (Model)

type alias MyType = SomeType.Model

type alias SameType = Model
```

The single file exporter exists because it keeps exports trivial, even if it
doesn't match Elm's module conventions.
